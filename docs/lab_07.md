## Транзакции и гонки

### Задание 1. Перевод

`transfer(from_id, to_id, amount)` работает так:

1. `BEGIN`.
2. `SELECT ... WHERE id IN (from, to) ORDER BY id FOR UPDATE`. Обе строки блокируются **в одном порядке**, поэтому
   встречные переводы A→B и B→A не попадут в deadlock.
3. Проверка: оба счёта существуют и баланс ≥ суммы.
4. Два `UPDATE`.
5. `COMMIT`; при любой ошибке `ROLLBACK`.

```
перевод 300 1->2:  {1: 700.00, 2: 800.00}
перевод 5000 2->1: InsufficientFunds; ROLLBACK, балансы {1: 700.00, 2: 800.00}
перевод на счёт 99: AccountNotFound; ROLLBACK, балансы не изменились
```

Атомарность: деньги не могут списаться без зачисления. Дополнительно стоит `CHECK (balance >= 0)` на случай ошибки в
коде.

### Задания 2 и 4. Гонка за последнее место (5 потоков одновременно, 1 место)

| Способ | Осталось мест | Регистраций | Комментарий |
|---|---|---|---|
| Наивный: `SELECT seats` → пауза → `UPDATE seats - 1` | **−4** | **5** | все 5 потоков прочитали `seats = 1` и прошли проверку |
| Наивный, но в таблице `CHECK (seats >= 0)` | 0 | 1 | 4 потока упали с `CheckViolation`; данные целы, но пользователь получил 500 |
| `SELECT ... FOR UPDATE` | 0 | 1 | потоки встали в очередь на блокировке строки, остальные увидели 0 мест; ~214 мс |
| Атомарный `UPDATE ... WHERE seats > 0` + `rowcount` | 0 | 1 | проверка и изменение в одном операторе; **~11 мс** |

**Сравнение FOR UPDATE и атомарного UPDATE.** `FOR UPDATE` нужен, когда между чтением и записью есть логика: проверить
несколько условий, посчитать сумму. Атомарный `UPDATE` проще и быстрее: строка блокируется на время одного оператора,
а не всей транзакции. Но он подходит, только если условие можно записать в `WHERE`. `rowcount = 0` означает «мест нет»,
`1` — «успешно». В приложении выдача книги сделана атомарным вариантом (`BookRepository.take_copy`). Тест
`test_concurrent_borrow_of_last_copy`: 10 читателей одновременно берут последний экземпляр, ровно один получает 201,
девять получают 409.

### Задание 3. UNIQUE

`registrations(user_id, course_id) UNIQUE`. Повторная запись даёт `psycopg2.errors.UniqueViolation`, который
перехватывается и превращается в `AlreadyRegistered("Вы уже записаны на этот курс")`. В API аналог — частичный
уникальный индекс `uq_loans_active_user_book ... WHERE returned_at IS NULL`: даже если два запроса одного читателя
проскочат проверку в сервисе, вторую активную выдачу не даст БД, а клиент получит 409.

## Индексы и EXPLAIN (50 000 строк)

### Задания 5 и 6

| Запрос | До индекса | После | Индекс |
|---|---|---|---|
| `WHERE email = '...'` | Seq Scan, cost 1093, 11,0 мс | Index Scan, cost 8,4, **0,18 мс** | `idx_users_email (email)` |
| `WHERE name = 'John' AND age = 30` | Seq Scan, cost 1218, 7,8 мс | Index Scan, cost 8,3, **0,09 мс** | `idx_users_name_age (name, age)` |
| `WHERE age = 30` | Seq Scan, cost 1093, 6,5 мс | Bitmap Heap Scan, cost 501, 0,77 мс | `idx_users_age (age)` |
| `WHERE active AND city = 'Moscow'` | Seq Scan, cost 1093, 7,8 мс | Bitmap Heap Scan, cost 575, 0,09 мс | `idx_users_active_city (city) WHERE active` — частичный |

**Почему до индексов везде Seq Scan:** индексов нет, кроме первичного ключа. **Почему по `age` не Index Scan, а
Bitmap:** возрастов всего 60, одному значению соответствует ~830 строк (1,7 %). Выгоднее собрать битовую карту страниц
и прочитать их по порядку, чем прыгать по индексу. Если бы условию соответствовала большая часть таблицы, планировщик
вообще выбрал бы Seq Scan: читать всё подряд дешевле. Для `active = true` (90 % строк) отдельный индекс по `active`
бесполезен, поэтому сделан **частичный** индекс по `city` только для активных.

### Задание 9. Правило левого префикса — индекс `(name, age, city)`

| Условие | Индекс используется? | Почему |
|---|---|---|
| `name = 'John'` | да (Bitmap, cost 151) | `name` — первая колонка индекса |
| `name AND age` | да (Index Scan, cost 8,3) | префикс `(name, age)` |
| `age = 30` | **нет** (Seq Scan) | нет первой колонки: по B-дереву нельзя искать с середины ключа |
| `city = 'Moscow'` | **нет** (Seq Scan) | то же |
| `name AND city` | да, частично (cost 23) | поиск идёт по `name`, а `city` фильтруется внутри найденного диапазона, пропуская `age` |

Правило: составной индекс работает для условий на его **левую часть** — `(a)`, `(a, b)`, `(a, b, c)`. Для запросов
по `age` и `city` нужны отдельные индексы, `idx_users_age` и частичный по `city`.

### Задание 10. Медленный отчёт по заказам (200 000 заказов)

```sql
SELECT u.name, u.email, COUNT(o.id), SUM(o.total) AS total_spent
FROM users u JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed' AND o.created_at > '2024-06-01'
GROUP BY u.id, u.name, u.email ORDER BY total_spent DESC LIMIT 20;
```

- До: `Seq Scan on orders` (все 200 тысяч строк) → Hash Join → HashAggregate; cost 7073, **91,5 мс**.
- Индекс `CREATE INDEX idx_orders_status_created ON orders (status, created_at) INCLUDE (user_id, total)`. Колонки
  идут в порядке «равенство, потом диапазон», а `INCLUDE` даёт агрегату нужные поля прямо из индекса.
- После: `Bitmap Index Scan on idx_orders_status_created` → Hash Join; cost 4851, **55,2 мс**, ускорение в 1,7 раза.
  Дальше упираемся не в поиск заказов (под фильтр попадает ~7 %, около 14 тысяч строк), а в Hash Join с таблицей
  пользователей и группировку.

## N+1 (100 читателей × 5 выдач)

### Задание 7. Сырой SQL

| Способ | Запросов | Время |
|---|---|---|
| N+1: список пользователей, затем `SELECT ... WHERE user_id = %s` в цикле | **101** | 29,4 мс |
| Один `LEFT JOIN` | 1 | **1,1 мс** |
| Пользователи + `WHERE user_id = ANY(%s)`, группировка в Python | 2 | 1,5 мс |

Время N+1 почти целиком уходит на сетевые обходы (round-trips): каждый запрос — это поход в БД и обратно. Через сеть
Docker или в другой дата-центр разница будет ещё больше.

### Задание 8. SQLAlchemy

| Метод | SQL-запросов | Время |
|---|---|---|
| `get_users_without_eager` (lazy) | **101** | 146,5 мс |
| `joinedload` | 1 (`LEFT OUTER JOIN`) | 14,2 мс |
| `subqueryload` | 2 (второй — с подзапросом исходного SELECT) | 13,8 мс |
| `selectinload` | 2 (второй — `WHERE user_id IN (...)`) | 14,4 мс |

Число запросов считается обработчиком события `before_cursor_execute`. Тот же SQL можно увидеть с
`create_engine(echo=True)` (`DB_ECHO=true` в настройках приложения).

**Что выбирать:**

- `joinedload` — для связи «многие к одному» и небольших коллекций;
- `selectinload` — для коллекций «один ко многим», не размножает строки родителя и хорошо работает с пагинацией.
  В приложении он используется в `UserRepository.list_with_loans`.
