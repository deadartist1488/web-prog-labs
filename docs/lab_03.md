# Лаба 3. Валидация и обработка ошибок (занятие 4)

**Что сделано.** Проверки разделены на три уровня, а все ошибки возвращаются в одном формате с `request_id`.
Ошибки логируются в JSON, пароли и токены при этом маскируются.

| Уровень | Где | Что проверяет | Код |
|---|---|---|---|
| Формат | `app/schemas.py` (Pydantic) | тип, обязательность, длина, диапазон, формат email/ISBN, лишние поля | **400** `VALIDATION_ERROR` |
| Бизнес-правила | `app/services/*` | пароль ≠ логину, лимит 5 книг, нельзя удалить аккаунт с книгами на руках, нельзя уменьшить тираж ниже выданного | **422** `BUSINESS_RULE_VIOLATION` |
| Состояние данных | сервисы + ограничения БД | уникальность email/ISBN, книга уже на руках, нет экземпляров | **409** `CONFLICT` |
| Доступ | `app/deps.py` | нет токена / нет прав | 401 / 403 |
| Сбои | `app/errors.py`, `app/middleware.py` | БД недоступна, непойманное исключение | 503 / 500 |

Если гонку не поймала проверка в сервисе, её поймает ограничение БД. `IntegrityError` превращается в 409, а не в 500.

Формат любой ошибки:

```json
{"error": {"code": "CONFLICT", "message": "Пользователь с таким email уже существует",
           "details": [{"field": "email", "message": "email уже занят"}],
           "request_id": "721570bd505f3cbc9e039d883d3be20e"}}
```

Тот же `request_id` приходит в заголовке `X-Request-ID` и пишется в каждую строку лога этого запроса.

## Ответы на задания

### Задание 1. `{"name":"J","email":"invalid-email","age":15,"password":"123"}`

1. Не пройдут **все четыре** проверки: name короче 2 символов, email без `@`, age < 18, password короче 8 символов.
2. Код **400 Bad Request**. Все ошибки отдаются сразу, а не только первая.
3–4. Ответ нашего сервера (реальный, см. `outputs/api_demo.txt`):

```json
{"error": {"code": "VALIDATION_ERROR", "message": "Данные запроса не прошли проверку", "details": [
  {"field": "name", "message": "String should have at least 2 characters", "type": "string_too_short"},
  {"field": "email", "message": "value is not a valid email address: An email address must have an @-sign.", "type": "value_error"},
  {"field": "age", "message": "Input should be greater than or equal to 18", "type": "greater_than_equal"},
  {"field": "password", "message": "String should have at least 8 characters", "type": "string_too_short"}],
  "request_id": "..."}}
```

### Задание 2. Отсутствует / null / "" / 0 / false

| Случай | Значение | Что означает |
|---|---|---|
| Поле отсутствует | ключа нет | «не передано»: в PATCH — не менять, в POST — ошибка, если поле обязательное |
| `null` | явное «нет значения» | «очистить», если поле может быть пустым; у нас `{"email": null}` в PATCH → 400 |
| `""` | пустая строка | значение есть, но пустое; для email/имени не проходит формат |
| `0` | число ноль | валидное число: возраст 0 не пройдёт диапазон, а цена 0 — допустимая бесплатная книга |
| `false` | логическое «нет» | осмысленное значение (`available=false` — выдать только недоступные книги) |

Отсутствие и `null` в коде различаются через `model_fields_set` (`UserPatch`), тест
`test_patch_distinguishes_missing_and_null`.

### Задание 4. Бизнес-правила

- **Пользователь.**
  - Регистрация: email уникален, возраст 18+, пароль ≠ email, письмо подтверждения уходит в очередь.
  - Смена email: новый адрес не занят, повторное подтверждение.
  - Удаление аккаунта: только сам или admin; нельзя, пока на руках книги (у нас 422); персональные данные удаляются,
    история выдач обезличивается.
- **Заказ / выдача книги.**
  - Создание: товар есть на складе (у нас: есть свободный экземпляр), лимит активных (у нас 5 книг), нельзя дважды
    взять одну книгу.
  - Смена статуса только по графу `new → paid → shipped → completed`, назад нельзя.
  - Отмена: только до отгрузки; при отмене остатки возвращаются (у нас возврат книги увеличивает `copies_available`).
- **Комментарий / отзыв.**
  - Добавить может только авторизованный, один отзыв на книгу (409), оценка 1–5.
  - Удалить может автор или admin (403 для остальных).

### Задание 5. Структуры ошибок

```json
// 1. несколько полей — 400
{"error": {"code": "VALIDATION_ERROR", "message": "Данные запроса не прошли проверку",
  "details": [{"field": "email", "message": "..."}, {"field": "age", "message": "..."}], "request_id": "..."}}
// 2. дубликат email — 409
{"error": {"code": "CONFLICT", "message": "Пользователь с таким email уже существует",
  "details": [{"field": "email", "message": "email уже занят"}], "request_id": "..."}}
// 3. не найден — 404
{"error": {"code": "NOT_FOUND", "message": "Пользователь 999 не найден", "details": [], "request_id": "..."}}
// 4. 500 — без стека и внутренностей, только request_id для поиска в логах
{"error": {"code": "INTERNAL_ERROR", "message": "Внутренняя ошибка сервера", "details": [], "request_id": "..."}}
```

### Задание 6. Сценарии для «создания пользователя»

- **Обычные:**
  1. Валидные данные → 201, в БД появилась запись, пароль сохранён хешем.
  2. Email в верхнем регистре → сохраняется в нижнем.
- **Граничные:**
  1. Возраст 18 и 120 проходят, 17 и 121 — нет.
  2. Имя длиной ровно 2 и ровно 50 символов проходит, 1 и 51 — нет.
- **Ошибочные:**
  1. Невалидный email → 400.
  2. Дубликат email (в том числе в другом регистре) → 409.
  3. `age: "abc"`, лишнее поле `role` или битый JSON → 400.

Всё это есть в тестах: `tests/test_users_api.py`, `tests/test_validation_and_examples.py`.

### Задание 7. Обработка ошибок

```python
def create_user(request):
    try:
        data = UserCreate.model_validate_json(request.body)       # формат
        user = user_service.create(data)                           # бизнес-правила + БД
        return 201, UserOut.model_validate(user)
    except ValidationError as e:
        log.warning("validation failed", extra={"context": {"fields": [x["loc"] for x in e.errors()]}})
        return 400, error_body("VALIDATION_ERROR", "Данные не прошли проверку", to_details(e))
    except BusinessRuleError as e:
        return 422, error_body(e.code, e.message, e.details)
    except DatabaseError as e:
        db.rollback()
        log.error("db error", exc_info=e)
        return 503, error_body("SERVICE_UNAVAILABLE", "База данных временно недоступна")
    except Exception as e:
        log.exception("unhandled")                  # стек — только в лог
        return 500, error_body("INTERNAL_ERROR", "Внутренняя ошибка сервера")
```

В проекте то же самое сделано централизованно через обработчики исключений FastAPI (`app/errors.py`), поэтому
хендлеры остаются короткими.

### Задание 8. Что логировать

| Что | Логировать | Почему |
|---|---|---|
| Пароль | **нет** | секрет; в логах маскируется как `***` (`mask_sensitive`) |
| Email | осторожно | персональные данные: только при неудачном входе (для разбора атак), лучше маскировать |
| Стек ошибки | да | без него не найти причину, но только в лог, не клиенту |
| IP клиента | да | безопасность и rate limit (`client_ip` в access-логе) |
| User-Agent | да | диагностика (в access-логе nginx) |
| Токен | **нет** | утёкший токен = доступ к аккаунту |
| Время выполнения | да | `duration_ms` в каждой строке access-лога |
| SQL-запрос | только текст без значений и только в debug | значения могут содержать персональные данные |

### Задание 9. `ValueError: invalid literal for int() with base 10: 'abc'`

1. Строку `"abc"` попытались привести к числу прямо в бизнес-логике, и это кончилось необработанным исключением, то
   есть 500.
2. Валидация должна быть на входе, до бизнес-логики, на уровне схемы запроса.
3. Клиенту надо вернуть **400**, а не 500: виноваты данные клиента.
4. Сообщить, что поле `age` должно быть целым числом. У нас:
   `{"field":"age","message":"Input should be a valid integer","type":"int_type"}`.
5. Исправление: схема со `strict`-типом `int` (`Age = Annotated[int, Field(ge=18, le=120, strict=True)]`) плюс общий
   обработчик ошибок валидации. Проверено тестом `test_create_user_bad_types_missing_and_extra_fields`.

### Задание 10. Реализация валидации

Реализовано в `app/schemas.py`:

- `NameStr`: 2–50 символов, только буквы, пробел и дефис, пробелы по краям обрезаются;
- `Email`: формат проверяется, адрес приводится к нижнему регистру;
- `Age`: строгий `int` от 18 до 120;
- `Password`: 8–72 символа, обязательно есть и буквы, и цифры.

Уникальность email проверяется в `UserService.create` (409), а «пароль ≠ логину» там же (422).
Для обновления сделаны отдельные схемы:

- `UserReplace` для PUT — все поля обязательны;
- `UserPatch` для PATCH — хотя бы одно поле, `null` запрещён.

Кастомные ошибки описаны иерархией `AppError` → `ValidationAppError`, `NotFoundError`, `ConflictError`,
`BusinessRuleError`... Ошибки валидации логируются на уровне WARNING со списком полей, но без значений.
