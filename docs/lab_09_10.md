# Лабы 9 и 10 (дополнительные). Диагностика, Redis, фоновые задачи (занятия 12–14)

## Лаба 9. Интеграционные тесты и диагностика

**Request ID** (`app/middleware.py`):

- у каждого запроса есть id: берётся из входящего `X-Request-ID`, если он похож на id (8–64 символа `[A-Za-z0-9-_.]`),
  иначе генерируется `uuid4`;
- id хранится в `contextvars`, поэтому попадает в **каждую** строку лога этого запроса, в тело любой ошибки
  (`error.request_id`) и в заголовок ответа `X-Request-ID`;
- nginx генерирует свой `$request_id`, передаёт его приложению (`proxy_set_header X-Request-ID`) и пишет в
  `access.log`, так что один id проходит через nginx, приложение и логи;
- при вызове внешнего сервиса тот же id надо передать дальше заголовком `X-Request-ID`, тогда цепочка не рвётся.

**Структурированное логирование** (`app/logging_setup.py`): одна JSON-строка на событие с полями `ts` (UTC), `level`,
`logger`, `request_id`, `msg`, `context` и `exc` (стек). Пароли и токены в `context` автоматически заменяются на `***`.
Access-лог пишет метод, путь, статус, `duration_ms`, IP и query.

### Задание 4. Воспроизведение ошибки по request_id

`GET /debug/flaky?fail_rate=0.3` падает примерно в 30 % случаев.

1. Клиент получает 500 и `{"error":{"code":"INTERNAL_ERROR",...,"request_id":"23de06ed..."}}`. Стека в ответе нет.
2. По этому id ищем логи: [`outputs/log_trace.txt`](outputs/log_trace.txt):

```
flaky: start                       {"roll": 0.334, "fail_rate": 1.0}
flaky: dividing by remaining stock
unhandled error on GET /debug/flaky   exc: ZeroDivisionError: division by zero (routers/web.py)
GET /debug/flaky - 500 - 0.015s
```

3. Последовательность событий ясна: деление на остаток, равный 0.
4. Тест, воспроизводящий проблему: `test_flaky_failure_can_be_traced_by_request_id`. Он вызывает эндпоинт с
   `fail_rate=1` (детерминированно), достаёт `request_id` из ответа и проверяет, что по нему находятся все записи,
   включая стек.

### Задания 1, 6, 7, 8. Интеграционные тесты и тестовое окружение

- **Реальная БД.**
  - `tests/test_postgres.py` работает на PostgreSQL.
  - Отдельная тестовая БД `library_test` поднимается через `pgserver` или берётся из `TEST_DATABASE_URL`.
  - Fixture `pg_app` готовит приложение, после теста выполняется `TRUNCATE ... RESTART IDENTITY CASCADE`.
  - Результат проверяется прямым SQL-запросом в БД (`test_create_user_is_really_in_postgres`).
- **Тестовое окружение в Docker.** [`docker-compose.test.yml`](../docker-compose.test.yml): PostgreSQL на 5433 и Redis
  на 6380, данные БД в `tmpfs`.
  1. `docker compose -f docker-compose.test.yml up -d`.
  2. `TEST_DATABASE_URL=postgresql://test:test@localhost:5433/test_db pytest -m postgres`.
  3. `docker compose -f docker-compose.test.yml down -v`.
- **Независимость тестов.**
  - Каждый тест получает новое приложение: SQLite в памяти + `flushall()` для fakeredis.
  - В PostgreSQL-тестах после каждого теста выполняется TRUNCATE.
  - Время в тестах не используется напрямую; для истёкшего токена создаётся `TokenService(access_minutes=-1)`.
  - Внешних сервисов нет: отправка писем подменена, Redis — fakeredis.
- **Проверяем не только статус.**
  - Данные в БД: пароль хранится хешем.
  - Остаток книг после выдачи и возврата.
  - Побочные эффекты: письмо легло в очередь, worker его «отправил»; в кэше появился ключ с TTL.
  - Логи: есть строка с нужным request_id.

### Задание 9. Метрики и алерты

|---|---|---|

- `EmailQueueGrowing` — очередь больше 100 (worker упал);
- `InstanceDown`.

## Лаба 10. Redis и фоновые задачи

**Cache-aside** (`app/infra.py: Cache`, `BookService.get_cached`):

1. `GET /books/{id}` сначала ищет `book:{id}` в Redis.
2. Промах → чтение из БД → запись в Redis с TTL 60 с.
3. Изменение, удаление, выдача и возврат книги сбрасывают ключ, поэтому устаревший остаток не показывается.
4. Если Redis недоступен, запрос идёт напрямую в БД и не падает (`test_cache_bypass_when_redis_down`).

Счётчики `hits`/`misses` проверены тестом `test_book_cache_aside_and_invalidation`: первый запрос — miss, второй — hit.

**Фоновые задачи и очередь** (`EmailQueue` + `app/worker.py`):

- Регистрация не шлёт письмо сама, а кладёт задачу в список Redis `queue:emails` (`RPUSH`). Ответ клиенту не ждёт
  SMTP.
- Отдельный контейнер `worker` (`python -m app.worker`) забирает задачи (`LPOP`) и отправляет. В учебной версии
  «отправка» кладёт письмо в `emails:sent`, это проверяется в тестах.
- Ошибка отправки возвращает задачу в очередь, следующая итерация повторяет попытку
  (`test_queue_is_idempotent_and_retries_failures`).
- Размер очереди виден в `/health`, `/metrics` и `/admin/email-queue` (только admin).

**Идемпотентные обработчики:**

- **Задачи.** Перед отправкой worker делает `SET job:done:{id} NX EX 7d`. Если ключ уже есть, та же задача уже
  выполнялась (повторная доставка), и она пропускается. У приветственного письма детерминированный id
  `welcome-{user_id}`.
- **HTTP.** `POST /books/{id}/loans` принимает заголовок `Idempotency-Key`. Ответ сохраняется в Redis на 24 часа, и
  повтор с тем же ключом возвращает **тот же** ответ с `Idempotent-Replay: true`, не создавая вторую выдачу. Это
  проверено и тестом, и вживую через nginx (`outputs/api_demo.txt`).

**Где ещё используется Redis:**

- blacklist JWT;
- refresh-токены;
- серверные сессии;
- счётчики неудачных входов.

У всех ключей есть TTL, поэтому Redis не разрастается. В Docker работает `redis:7-alpine` с `appendonly yes`, чтобы
данные пережили перезапуск. Для разработки без Docker хватает `REDIS_URL=fake://` (fakeredis в памяти) или
`scripts/local_redis.py`, если нужен общий Redis для двух экземпляров.

**Почему Redis, а не RabbitMQ.** Для очереди писем хватает списка в Redis: Redis уже есть в стенде, а задачи
идемпотентны, так что редкий дубль не страшен. RabbitMQ стоит брать, когда нужны подтверждения доставки (ack),
маршрутизация, приоритеты и гарантии «хотя бы один раз» на уровне брокера.
