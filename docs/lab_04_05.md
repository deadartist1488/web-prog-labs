# Лабы 4 и 5. Архитектура и тестирование (занятия 5–6)

## Лаба 4. Слои, DI, конфигурация, БД

```
            HTTP
              │
   ┌──────────▼───────────┐  app/middleware.py: X-Request-ID, access-лог, метрики, заголовки безопасности
   │      Middleware      │
   └──────────┬───────────┘
   ┌──────────▼───────────┐  app/routers/*: разбор запроса, схема (Pydantic), код ответа.
   │  Handler (routers)   │  Бизнес-логики нет.
   └──────────┬───────────┘
              │ Depends(...)   ← app/deps.py собирает зависимости (DI)
   ┌──────────▼───────────┐  app/services/*: бизнес-правила, транзакции (commit/rollback),
   │   Service (services) │  побочные эффекты (очередь писем, кэш). Про HTTP не знает.
   └──────────┬───────────┘
   ┌──────────▼───────────┐  app/repositories/*: только SQL/ORM-запросы.
   │ Repository (repos)   │
   └──────────┬───────────┘
   ┌──────────▼───────────┐  app/db.py: engine + пул соединений; app/models.py: таблицы
   │ PostgreSQL / SQLite  │
   └──────────────────────┘
   Redis (app/infra.py): кэш, очередь, сессии, blacklist — передаётся в сервисы через DI
```

- **DI.** Сервис получает зависимости в конструкторе: `UserService(session, users_repo, loans_repo, email_queue)`.
  Сборка происходит в `app/deps.py` через `Depends`. Долгоживущие объекты (engine, Redis, TokenService) создаются один
  раз в `app_factory` и лежат в `app.state`, а сессия БД своя на каждый запрос. Благодаря этому в unit-тестах сервис
  собирается из `MagicMock`, а в API-тестах подменяется вся конфигурация (SQLite в памяти, fakeredis).
- **Конфигурация.** `app/config.py` (pydantic-settings) читает переменные окружения и `.env`. Для каждой есть значение
  по умолчанию, шаблон лежит в [`.env.example`](../.env.example), а `.env` добавлен в `.gitignore`.
- **БД.** SQLAlchemy 2.0 ORM, `QueuePool` (`pool_size=5`, `max_overflow=10`, `pool_pre_ping`). В разработке без
  настроек работает SQLite, в Docker — PostgreSQL. Миграции лежат в `migrations/*.sql`.
- **Обработка исключений на уровне handler** сделана централизованно (`app/errors.py`), **middleware логирования
  запросов** — в `app/middleware.py`.

### Задание 4. Побочные эффекты

| Функция | Побочный эффект? | Почему |
|---|---|---|
| `add` | нет | чистая: результат зависит только от аргументов |
| `save_user` | **да** | пишет в БД |
| `send_email` | **да** | сетевой вызов, письмо нельзя «отменить» |
| `get_user` | **да** (чтение внешнего состояния) | результат зависит от БД, это ввод-вывод |
| `log` | **да** | пишет в файл |
| `calculate_total` | нет | чистая |

Как изолировать побочные эффекты:

- держать их на краях системы (репозитории, отправители писем) и внедрять через DI, тогда в тестах их можно
  замокать;
- бизнес-логику оставлять чистой;
- письма слать после коммита и через очередь. У нас так и сделано: `UserService.create` → `email_queue.enqueue`.

### Задание 5. Архитектура блога

```
PostHandler ─► PostService ─► PostRepository ─► DB
                  │  ├────► TagRepository
                  │  └────► UserRepository (проверка автора)
CommentHandler ─► CommentService ─► CommentRepository, PostRepository
                                 └► NotificationService (письмо автору поста)
```

Handlers только переводят HTTP в вызовы. `PostService` создаёт пост (автор существует, теги нормализуются) и добавляет
тег (тег уникален в рамках поста). `CommentService` добавляет комментарий (пост существует и не закрыт) и уведомляет
автора поста. Репозитории отвечают только за запросы к БД.

### Задание 6. Рефакторинг `create_order`

```python
class OrderService:
    def __init__(self, session, users, products, orders, notifications):
        ...

    def create(self, user_id: int, items: list[OrderItemIn]) -> Order:
        user = self.users.get(user_id) or raise_(NotFoundError("User not found"))
        lines, total = [], Decimal(0)
        for item in items:                                   # бизнес-логика: проверка и расчёт
            product = self.products.get_for_update(item.product_id)        # блокируем строку
            if product is None:
                raise NotFoundError(...)
            if product.stock < item.quantity:
                raise ConflictError(...)
            lines.append((product, item.quantity, product.price))           # цену берём для КАЖДОЙ позиции
            total += product.price * item.quantity
        with self.session.begin():                            # одна транзакция на заказ, позиции и остатки
            order = self.orders.add(Order(user_id=user_id, total=total))
            for product, qty, price in lines:
                self.orders.add_item(order.id, product.id, qty, price)
                self.products.decrease_stock(product.id, qty)  # UPDATE ... WHERE stock >= qty
        self.notifications.order_created(user.email, order.id)  # побочный эффект после коммита, через очередь
        return order
```

Что исправлено:

- в исходном коде вставки шли без транзакции: при ошибке на середине оставался заказ без позиций;
- остаток проверялся без блокировки, что приводило к гонке;
- в `order_items` для всех позиций записывалась цена последнего `product` — это баг;
- письмо уходило до гарантии, что всё сохранилось.

У нас тот же подход в `LoanService.borrow`: атомарный `UPDATE` остатка, создание записи и один `commit`.

### Задание 7. Как тестировать слои

| Слой | Как тестировать | Что мокать |
|---|---|---|
| Handler | HTTP-тест через TestClient: коды, структура ответа, заголовки | сервис (или подставить тестовую конфигурацию: SQLite в памяти + fakeredis) |
| Service | unit-тесты бизнес-правил | репозитории, очередь, кэш (`MagicMock`) |
| Repository | интеграционный тест с настоящей БД | ничего: смысл в проверке реальных запросов |

Repository мокать не нужно: мок проверит только сам себя. Тесты репозиториев идут на PostgreSQL (`tests/test_postgres.py`).
